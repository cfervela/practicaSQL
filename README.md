# Gestor de tareas local (Flutter + SQLite)

Práctica de Programación de Dispositivos Móviles: aplicación de tareas con
persistencia local en SQLite, diseñada para Android, iOS, Windows, Linux,
macOS y web con una sola base de código.

## Estado del proyecto

- [x] Etapa 2: persistencia real (crear y consultar)
- [x] Etapa 3: editar, completar, eliminar y validar
- [ ] Etapa 4: web, pruebas y documentación de plataformas

## Funcionalidades

- Alta de tareas (F1), con validación del título.
- Consulta reactiva de las tareas guardadas (F2).
- Edición del título desde un diálogo (F3).
- Cambio de estado completada/pendiente con la casilla (F4).
- Eliminación por identificador, con confirmación (F5).
- Funciona sin conexión; no hay solicitudes HTTP (F6).

## Tecnología de persistencia elegida

**Drift + drift_flutter** (sobre SQLite).

Motivos:
- [Un mismo código para las tres plataformas mediante `driftDatabase`.]
- [Tablas definidas en Dart y consultas tipadas, en vez de SQL en cadenas.]
- [Consultas reactivas con `Stream` (`watch()`), que evitan consultar a
  mano después de cada escritura.]
- [Soporte web mediante WebAssembly.]

Alternativas descartadas:
- `sqflite`: [por qué no cubre bien web y escritorio].
- `sqlite3` directo: [más trabajo manual de SQL y mapeo].
- `shared_preferences` con JSON o lista en memoria: no cumplen el requisito
  de SQLite real.

Dependencias previstas: `drift`, `drift_flutter` y, en desarrollo,
`drift_dev` y `build_runner` (genera el código de la base).


## Diseño de la tabla `tareas`
| Column | SQLite type | Constraints | Reason |
| --- | --- | --- | --- |
| `id`| `INTERGER` | `PRIMARY KEY AUTOINCREMENT` | Unique identifier, generated by the database. With `AUTOINCREMENT`, ids of deleted rows are not reused. |
| `titulo`| `TEXT` | `NOT NULL` | The task title. Validation (no empty or whitespace-only titles) also lives in Dart. | 
| `completada`| `INTERGER` | `NOT NULL DEFAULT 0` | TSQLite has no real boolean, so 0 = pending and 1 = completed. Drift's boolean() maps this for you. | 

**Identificación de registros:** cada tarea se identifica por `id`,
generado por la base de datos. Editar, cambiar estado y eliminar usan
`WHERE id = ?`, porque los títulos pueden repetirse.

**Validación:** [no se acepta un título vacío o de solo espacios; se
recorta con `trim()` antes de guardar].

## Operaciones (`lib/data/database.dart`)

| Operación        | SQL    | Método                            | Resultado |
|------------------|--------|-----------------------------------|-----------|
| Consultar        | SELECT | `observarTareas()` (Stream)       | Lista, se re-emite al cambiar la tabla |
| Agregar          | INSERT | `agregarTarea(titulo)`            | id nuevo |
| Editar título    | UPDATE | `actualizarTitulo(id, titulo)`    | `false` si la tarea ya no existe |
| Cambiar estado   | UPDATE | `cambiarEstado(id, completada)`   | `false` si la tarea ya no existe |
| Eliminar         | DELETE | `eliminarTarea(id)`               | `false` si la tarea ya no existe |


## Validación y mensajes de error

La validación está en `lib/utils/validacion.dart` y se aplica en dos capas:
la pantalla (para dar el mensaje de inmediato) y la capa de datos (para que
no se pueda guardar un título inválido aunque se llame a la base directamente).

- El título se recorta con `trim()`; vacío o solo espacios se rechaza.
- Longitud máxima de 100 caracteres, igual que la restricción de la tabla.
- Los errores de validación muestran su mensaje; cualquier otro error de
  almacenamiento se convierte en un mensaje comprensible, por ejemplo
  "No se pudo guardar la tarea. Inténtalo de nuevo.".
- Si una tarea ya no existe (por ejemplo, se borró desde otra pestaña), se
  informa "La tarea ya no existe.".

## Estructura

- `lib/main.dart`: arranque; crea la base una sola vez y la pasa a la pantalla.
- `lib/data/database.dart`: tabla, apertura de la base y operaciones.
- `lib/models/tarea.dart`: modelo de tarea.
- `lib/utils/validacion.dart`: reglas de validación del título.
- `lib/screens/tareas_page.dart`: interfaz; se suscribe al stream en
  `initState` y cancela la suscripción en `dispose`, sin consultas dentro de
  `build()`.
- `web/sqlite3.wasm` y `web/[nombre del worker]`: recursos de Drift para web.

## Cómo ejecutar

    flutter pub get
    dart run build_runner build
    flutter analyze
    flutter test
    flutter run -d web-server --web-port=8080

   Abrir http://localhost:8080 en el navegador. Se usa un puerto fijo porque en la web los datos están ligados al origen (dominio y puerto); con otro puerto se vería una base distinta y vacía.

### Recursos de la web

`sqlite3.wasm` y el worker de Drift se descargaron de los releases de Drift (versión [2.35.4], la misma que aparece en `pubspec.lock`) y se colocaron en `web/`. El nombre del worker en `web/` debe coincidir con el usado en `DriftWebOptions` en `lib/data/database.dart`.

## Limitaciones conocidas

- En la web la base pertenece al origen y al perfil del navegador: otro puerto, otro navegador o borrar los datos del sitio implican una base distinta o vacía.
- En ventanas privadas el navegador puede usar almacenamiento temporal.
- Aún no se pueden editar, completar ni eliminar tareas (etapa 3).

## Dificultad técnica: temporizador pendiente en la prueba de widget

Al agregar Drift, la prueba básica de inicio falló con el error `A Timer is still pending even after the widget tree was disposed`. La traza señalaba `StreamQueryStore.markAsClosed` de Drift, llamado desde el `dispose()` de `TareasPage`, donde cancelo la suscripción al stream de tareas. Entendí que al cancelarse el último oyente de un stream, Drift programa un temporizador de limpieza, y que en la prueba la pantalla se desmontaba hasta el final, cuando ya no había oportunidad de ejecutarlo. El código de la aplicación era correcto: cancelar la suscripción es lo que pide el requisito de liberar recursos.

Lo resolví desmontando la pantalla dentro de la propia prueba (`pumpWidget(const SizedBox.shrink())`) y avanzando el reloj simulado (`pump(Duration.zero)`), y cerrando la base en `addTearDown`. Lo verifiqué ejecutando de nuevo `flutter test` [: la prueba pasó / resultado observado]. Además agregué una prueba de almacenamiento sin widgets (`test/database_test.dart`) con una base en memoria, que no depende del reloj simulado de las pruebas de widget.

## Referencias consultadas
- **Drift, documentación general** (https://drift.simonbinder.eu/):
  aprendí que Drift permite definir las tablas como clases de Dart y que
  genera el código de acceso con `build_runner`, con consultas tipadas y
  consultas reactivas (`watch()`), en lugar de escribir SQL en cadenas.
- **drift_flutter en pub.dev** (https://pub.dev/packages/drift_flutter):
  aprendí que ofrece la función `driftDatabase`, que abre la base de datos
  adecuada para cada plataforma, y que en la web requiere colocar
  `sqlite3.wasm` y `drift_worker.js` en la carpeta `web/`.
- **sqlite3 en pub.dev** (https://pub.dev/packages/sqlite3): aprendí que es
  el paquete de bajo nivel (FFI y WebAssembly) sobre el que se apoya
  Drift, y que usarlo directamente implicaría escribir yo el SQL y el
  mapeo de datos.
- **sqflite en pub.dev** (https://pub.dev/packages/sqflite): aprendí que
  está orientado a Android, iOS y macOS, por lo que no cubre por sí solo
  web y escritorio; por eso lo descarté.
- **SQLite, "Datatypes In SQLite"** (https://www.sqlite.org/datatype3.html):
  aprendí que SQLite usa afinidades de tipo (INTEGER, TEXT, REAL, BLOB,
  NUMERIC) y que no tiene un tipo booleano real, así que `completada` se
  guarda como entero 0 o 1.
- **SQLite, "SQL As Understood By SQLite"** (https://www.sqlite.org/lang.html):
  repasé la sintaxis de `INSERT`, `SELECT`, `UPDATE` y `DELETE`, y de
  `PRIMARY KEY AUTOINCREMENT`, que uso para generar el identificador único.
